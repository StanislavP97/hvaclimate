# Feature: SEO layer

**From build-plan:** feature 15
**Status:** complete

## Goal

Complete the site's SEO surface so it's crawlable and correctly indexed under its
own domain: fix the placeholder root metadata, generate `sitemap.xml` and
`robots.txt`, and add JSON-LD structured data (LocalBusiness sitewide, Service on
service sub-pages). Per-route `generateMetadata()` / `metadata` exports already
exist on all 21 page routes (confirmed by audit) - this feature fills the gaps
around them, it doesn't redo them.

## Audit findings (why these steps, not others)

- All static pages (`/`, `/about`, `/contact`, `/privacy-policy`, `/instant-quote`,
  `/blog`, category pages) already export `metadata`. All dynamic `[slug]` routes
  already export `generateMetadata()` reading `titleTag`/`metaDescription` from
  CMS JSON. **No per-route work needed.**
- `app/layout.tsx`'s root `metadata` is still the create-next-app placeholder
  (`"Create Next App"` / `"Generated by create next app"`) with no
  `metadataBase`, no title template, no default OpenGraph/Twitter card. This is
  the fallback for any page that doesn't override it, and the base for resolving
  relative OG image URLs - it's currently wrong.
- No `sitemap.xml`, `robots.txt`, or JSON-LD (`application/ld+json`) exist
  anywhere in the repo (confirmed via grep).
- No canonical site URL constant exists yet - needed for `metadataBase`, sitemap
  absolute URLs, and JSON-LD `url`/`@id` fields.
- Business identity (name, phone, address) is currently hardcoded ad hoc in
  `Footer.tsx`/`Header.tsx` (`(360) 888-2217`, `7933 NE St Johns Rd, Vancouver,
  WA`). This feature reads those same values into one shared constants module
  rather than re-deriving them, so JSON-LD and sitemap stay consistent with what's
  already on the page.

## In scope

- Fix root layout metadata: real title/description, title template
  (`%s | HVA Climate Control`), `metadataBase`, default OpenGraph + Twitter card.
- One shared `lib/site.ts` (or similar) constant module: site URL, business name,
  phone, address - sourced from what's already displayed in Footer/Header.
- `app/sitemap.ts` (Next.js MetadataRoute.Sitemap) covering all 22 routes from the
  URL map, including every dynamic `[slug]` entry pulled from each collection's
  JSON via existing `lib/*.ts` getters.
- `app/robots.ts` (Next.js MetadataRoute.Robots): allow all, point to the sitemap.
- Sitewide `LocalBusiness` JSON-LD in the root layout (name, phone, address,
  url, areaServed).
- `Service` JSON-LD on the service sub-page detail template
  (`ServiceDetailLayout`, shared by gas-furnace, electric-furnace, ac-repair,
  ac-installation, ac-tuneup, ductwork, vent-cleaning, commercial, service-areas,
  rebate-programs) - one addition covers all those routes since they share the
  component.
- `metadata` export for `app/not-found.tsx` (currently missing).

## Out of scope

- Rewriting or auditing the per-route `title`/`description` values already in
  place - they're populated from CMS JSON and correct.
- Google Search Console verification, actual submission of the sitemap.
- BlogPosting JSON-LD for blog posts (not called out in the build-plan line item;
  can be a follow-up `/fix` if wanted).
- Reviews/ratings schema - that's feature 16 (GTM + Reviews).
- Performance work, `next/image` audit, 301 redirects - that's feature 17.
- Changing any URL slug.

## Build loop

Build one step at a time, never the whole feature at once.

1. Plan mode lays out the step before any code.
2. The AI implements just that step.
3. It shows the diff (not full files); you read it and understand it.
4. You approve, then choose whether to commit a checkpoint or roll straight on.
   Checkpoints are optional; `/complete` makes the real feature-level commit at the end.

Never accept a step you haven't read. If a diff is too big to review, the step was too big, so split it.

## Testing

- No `test` command declared in `AGENTS.md` yet, so this rides on build +
  browser evidence, not unit tests - consistent with the project's opt-in
  testing gate. `lib/site.ts` is a plain constants module (no branching logic),
  so it doesn't meet the "parsers/formatters/validators" bar that would demand
  a test even if a runner existed.
- Verify each step in the browser: view-source on representative pages,
  `/sitemap.xml`, `/robots.txt`, and a 404 route.
- Run `npm run build` after each step - a broken `generateStaticParams()` or
  malformed sitemap entry will surface as a build error.
